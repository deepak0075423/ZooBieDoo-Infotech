Implementing design tokens so a rebrand is a configuration change

Tokens turn visual decisions into named values shared by design and code. Naming them well is the whole trick.

ZooBieDoo Infotech Engineering Team 19 July 2026 · 6 min read

Key takeaways

  • Semantic names survive rebrands; value names do not.
  • Two layers: primitives holding values, semantics referencing them.
  • Generate platform outputs from one source of truth.
  • Theming becomes a value swap rather than a parallel stylesheet.

Name by role, not by value

A token called blue-500 describes what it is. A token called surface-interactive describes what it is for. The second survives a rebrand; the first requires renaming everything.

Use a two-layer approach: primitives holding raw values, and semantic tokens referencing them. Components consume only semantic tokens, so changing a brand colour is one edit at the primitive layer.

Cover more than colour

  • Spacing — a small scale people use consistently.
  • Typography — size, weight, line height and letter spacing as a set.
  • Radius, border and elevation — small sets prevent drift.
  • Motion — duration and easing named by purpose.

Undefined categories get improvised, and improvisation is where inconsistency enters.

One source, generated outputs

Keep tokens in one machine-readable file and generate the outputs each platform needs — CSS custom properties, platform constants, design tool variables.

Maintaining separate lists by hand guarantees divergence. Generation makes design and code agree by construction rather than by discipline.

Theming falls out for free

With semantic tokens, dark mode and brand variants become alternative value sets rather than parallel stylesheets. High contrast modes and white-label deployments work the same way.

This is usually the point at which the effort pays for itself, and it is worth structuring for even if theming is not an immediate requirement.

Migrating an existing product

Introducing tokens into a product with hard-coded values is a gradual process, and attempting it in one change is unwise.

Start by auditing what is actually used — the result is usually dozens of near-identical greys and a handful of arbitrary spacing values. Consolidate to a defensible set, then replace values component by component as each is touched.

Add linting that flags raw colour and spacing values in new code, so the problem stops growing while the migration proceeds. Without that, cleanup never overtakes accumulation.
