Core Web Vitals: what each metric measures and how to fix it

LCP, INP and CLS measure different failures with different causes. Knowing which metric is failing tells you almost exactly where to look.

ZooBieDoo Infotech Engineering Team 21 August 2026 · 8 min read

Key takeaways

  • Each metric has distinct causes — diagnose before optimising.
  • Server response time caps everything downstream.
  • Image dimensions, font loading and third-party scripts are the usual culprits.
  • Judge by field data at the 75th percentile, not laboratory scores.

The three metrics and what breaks them

Largest Contentful Paint measures how long the main content takes to appear. It fails when the hero image is unoptimised, when a render-blocking stylesheet delays paint, or when the server takes too long to respond in the first place.

Interaction to Next Paint measures responsiveness — how long the page takes to react after a user acts. It fails when long JavaScript tasks block the main thread, which is usually third-party scripts or an over-eager hydration step.

Cumulative Layout Shift measures visual stability. It fails when images and embeds have no declared dimensions, when fonts swap and reflow text, or when content is injected above what the user is already reading.

Fix the server before the front end

Time to First Byte sets the ceiling for everything else. If the server takes 800ms to respond, no amount of front-end tuning will produce a good Largest Contentful Paint.

Check caching first: are anonymous responses cached, is there a CDN in front, and does a cold cache produce an acceptable response? Then look at the application — uncached database queries on every request are the usual cause.

The highest-return front-end fixes

  • Give every image explicit width and height attributes, and serve modern formats at the size actually displayed.
  • Preload the font files used above the fold and use font-display: swap with a well-matched fallback to limit reflow.
  • Defer non-critical JavaScript and audit third-party tags against what they deliver.
  • Reserve space for anything injected after load — banners, embeds, advertisements.

These four changes account for the majority of improvement on a typical business site, and none of them requires re-architecting anything.

Measure from real users

Laboratory tools are useful for diagnosis and misleading as a scorecard, because they run on a fast connection from a nearby location. What counts is field data from actual visitors on actual devices.

Use the Chrome User Experience Report or your own real-user monitoring, look at the 75th percentile rather than the average, and segment by device. A site that is comfortable on desktop and failing on mid-range Android phones is the normal finding.

A prioritised remediation order

When several metrics fail at once, the order of work matters because the fixes interact. Start at the server: reduce time to first byte through caching and query work, because every other metric inherits that delay.

Then address the largest contentful element directly — usually a hero image or a web font. Serve it at display size in a modern format, preload it, and remove anything render-blocking ahead of it. This single step commonly resolves LCP outright.

Only then move to interaction and layout stability, which are mostly about deferring or removing JavaScript and declaring dimensions. Working in this order avoids the common trap of optimising images on a site whose real problem is a four-second server response.
